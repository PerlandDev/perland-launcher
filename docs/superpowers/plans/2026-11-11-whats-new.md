# What's New Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Players see what changed after each launcher update, from bilingual notes written per pull request.

**Architecture:** Notes are one JSON file each in `release-notes/`. Pure functions in `scripts/release/notes.mjs` give each note the version it first shipped in (from the release tags) and build one notes file plus the GitHub Release description. The UI bundles the notes file through a Vite virtual module; a pure rule decides what to show against a "last seen" marker the core keeps in `whats-new-seen.json`.

**Tech Stack:** Node 24 (`node:test`, no dependencies), GitHub Actions, Rust (`launcher-core`, `launcher-app`, Tauri commands), React + Vitest + zod.

**Spec:** `docs/superpowers/specs/2026-11-10-whats-new-design.md`. Writing rules for notes: `.claude/skills/release-notes/SKILL.md`.

## Global Constraints

- A note is `release-notes/<slug>.json` with exactly `kind`, `en`, `es`. Slug: `[a-z0-9]+(-[a-z0-9]+)*`. `kind`: `new`, `improved` or `fixed`. `en` and `es`: one line, 1 to 140 characters (counted in code points), no control characters, no `http://` or `https://`, none of `< > [ ] * \``.
- Releases that count: tags matching the existing `CALVER` pattern in `scripts/release/lib.mjs` that are ancestors of the commit being built. `v0.x` tags are ignored.
- A note's version (`since`): the oldest release such that it and every later one, up to the build, contain the note's file.
- The notes file holds the newest 10 base versions that have notes.
- The Release workflow never commits or pushes to the repository.
- A release must fail on a shallow clone; local dev and CI tests must work on one.
- Every UI string is in both `ui/src/i18n/en.json` and `ui/src/i18n/es.json`. Notes render as text, never as HTML.
- `launcher-core` and `launcher-app` never depend on Tauri or UI crates. TDD: the failing test first.
- UI styling goes through the `/impeccable` skill and `DESIGN.md`. Nothing glows, blurs or eases.
- Never run fuzzing, stress or load tests locally.
- Before each commit: the checks in `CLAUDE.md` ("Before committing") for the parts touched.

## Review Focus

1. A release built from a shallow clone: every note would look new. `notes` with a real version must refuse (Task 2).
2. A note file with a trailing newline or CRLF line endings must parse; a tab or newline inside `en`/`es` must be refused; 140 characters pass and 141 fail, counted in code points so "ñ" and "→" count once (Task 1).
3. `whats-new-seen.json` damaged, empty or holding a non-string reads as "no marker", and marking then repairs it (Task 3).
4. A launch where another dialog is open or a run is not idle when the dialog would open: no dialog, the marker does not move, and the next launch shows the same notes (Task 5).
5. A marker the notes file does not know (a beta from a branch that never merged) or newer than the running version (a downgrade): the first shows the running base version's notes, the second shows nothing (Task 4).

**Interfaces:**
- Produces (all exported from `notes.mjs`):
  - `KINDS = ['new', 'improved', 'fixed']`, `MAX_CHARS = 140`, `MAX_GROUPS = 10`
  - `parseNote(fileName: string, text: string): { id, kind, en, es }`. `fileName` is `whats-new.json`; `id` is the slug. Throws `Error` whose message starts with `release-notes/<fileName>: `.
  - `compareVersions(a: string, b: string): number` for `YYYY.M.MICRO` and `YYYY.M.MICRO-beta.N` (a beta sorts before its stable).
  - `releaseVersions(tags: string[]): string[]`: CalVer tags only, without the `v`, ascending.
  - `baseOf(version: string): string` (`2026.11.5-beta.2` → `2026.11.5`).
  - `assignVersions({ releases: { version, ids: string[] }[], current: { version: string | null, ids: string[] } }): Map<string, string | null>`. `releases` ascending. Keys are `current.ids`; the value is the note's `since`, or `null` when no release has it and `current.version` is `null`.
  - `buildNotes({ releases: { version, date, ids }[], current: { version: string | null, date: string, notes: Note[] }, cap = MAX_GROUPS }): NotesFile`
  - `releaseBody({ notes: NotesFile, version: string, footer: string }): string`
- `NotesFile` is `{ versions: string[], groups: { base: string | null, date: string, notes: { id, kind, since: string | null, en, es }[] }[] }`. `versions`: every release ascending, then `current.version` when it is not `null`. `groups`: newest base first, the `null` base ("next update") before all; a group's `date` is the date of its newest release (`current.date` for the build's own base and for `null`); notes ordered by `KINDS`, then `id`. Only bases with notes; at most `cap`.
